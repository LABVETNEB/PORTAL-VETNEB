## Context

`ERM-CTRL-024` remained `PARTIAL` with three separate open items: Dependabot security
updates disabled, no explicit Dependabot coverage for the `frontend` workspace, and no
executable SBOM generation.

The repository imposes hard constraints on any solution:

- `scripts/governance/workflow-security-policy.mjs` allows exactly five external action
  repositories and forbids job-level permissions entirely; top-level permissions must be
  exactly `contents: read`.
- `test/architecture/toolchain-contract.test.ts` forbids `continue-on-error` and `|| true`
  anywhere in `backend-ci.yml`.
- `test/unit/infrastructure/workflow-security-policy-contract.test.ts` pins the exact set of
  workflow files and a reviewed SHA-256 digest per workflow.
- The workspace uses pnpm 11 with `pnpm-lock.yaml`; there is no `package-lock.json`.
- Branch protection requires four contexts: `validate-pr-governance`,
  `qga-workflow-security`, `validate-backend` and `validate-frontend`.

## Decision

### 1. SBOM is generated by a repository-owned script

`scripts/supply-chain/generate-sbom.mjs` reads the committed `pnpm-lock.yaml` with the
already-pinned `js-yaml` devDependency and emits a CycloneDX 1.6 JSON document.

The document is deterministic for a given commit: `serialNumber` and `metadata.timestamp`
are omitted, and components are sorted by package URL. Component integrity digests are
converted from the lockfile Subresource Integrity values to CycloneDX hex hashes.

### 1.1 The BOM subject is the monorepo, not a single deployable

The lockfile is a single combined pnpm workspace inventory, so no individual application may
claim it. `metadata.component` is therefore an aggregate platform subject (`portal-vetneb`)
that carries no version and no package URL, and both deployables hang off it as explicit child
applications in `metadata.component.components`:

| Deployable | Manifest |
| --- | --- |
| Backend | `package.json` |
| Frontend | `frontend/package.json` |

Name, version and package URL are derived dynamically from each manifest; nothing is
hardcoded. The children live inside the subject and never enter `components`, so the lockfile
package count is not inflated. One artifact and one output file are preserved.

Manifest reading is fail-closed: an unreadable, non-JSON, non-object, unnamed, unversioned or
non-URL-encodable manifest, or two manifests resolving to the same package URL, aborts
generation. There is no `0.0.0` fallback that could hide an invalid manifest, and error
messages carry the manifest path and the reason only, never manifest content or absolute
paths.

### 2. SBOM runs as an isolated, structurally non-blocking job

The `generate-sbom` job lives in `.github/workflows/backend-ci.yml`. It declares no `needs`,
no job depends on it, and the required `validate-backend` context (`backend-check`) never
observes its result. Merge is therefore never blocked by SBOM generation, and no failure is
masked with `continue-on-error`.

The job uploads `sbom/portal-vetneb.cdx.json` as the stable artifact `sbom-cyclonedx` with
`retention-days: 90` and `if-no-files-found: error`.

### 3. Dependabot separates ecosystems and groups only low-risk updates

`.github/dependabot.yml` declares three independent entries: npm `/`, npm `/frontend` and
`github-actions` `/`. Each entry owns a distinct group namespace restricted to
`applies-to: version-updates` and `update-types: [minor, patch]`, so major updates are never
grouped and always arrive as isolated pull requests.

## Alternatives considered and rejected

| Alternative | Rejection reason |
| --- | --- |
| `CycloneDX/gh-node-module-generatebom` action | Not in `APPROVED_EXTERNAL_ACTIONS`. Adopting it would require an R2 change to the workflow security policy and would add a third-party action to the trusted set for evidence-only output. |
| `@cyclonedx/cyclonedx-npm` as a devDependency | Designed around npm `package-lock.json`; this workspace is pnpm-only. Adds a persistent dependency, lockfile churn and transitive audit surface with no compensating benefit. |
| `pnpm dlx <tool>@<exact-version>` | Resolves from the registry at run time, outside `pnpm install --frozen-lockfile`. Not reproducible against the lockfile and fails closed on registry incidents. |
| Downloading a `syft`/`cdxgen` binary | Requires `curl \| sh` or an unpinned release download. Explicitly forbidden by the supply-chain policy and by `AGENTS.md`. |
| A separate `.github/workflows/sbom.yml` file | Would break the frozen seven-workflow census for evidence-only output; the existing backend workflow already provides the pinned toolchain. |

## Preserved invariants

- The four required merge contexts and their job names are unchanged.
- Branch protection, Actions permissions and repository settings are unchanged.
- Top-level `permissions: contents: read` is preserved; no job-level permissions exist.
- All actions remain pinned to lowercase 40-character SHAs.
- `package.json` and `pnpm-lock.yaml` are unchanged; no dependency is added.
- No `continue-on-error` and no `|| true` is introduced.
- The generated SBOM stays untracked via `.gitignore`.

## Consequences

### Positive

- SBOM evidence exists per commit without a new dependency or third-party action.
- Output is byte-reproducible for a given lockfile, so drift is diffable.
- Major dependency updates keep an isolated review and rollback boundary.

### Trade-offs

- The generator is repository-owned code that must be maintained if the pnpm lockfile format
  changes; it is covered by contract tests.
- The SBOM reflects the lockfile graph, not a runtime scan; it does not detect vendored or
  dynamically loaded code.
- Backend CI gains one extra job on every pull request and push.
- Changing `backend-ci.yml` requires updating its reviewed SHA-256 integrity digest.

## Rollback

Revert the technical pull request. The Dependabot configuration returns to two entries, the
`generate-sbom` job disappears, the generator and its contracts are removed, and the reviewed
digest returns to its previous value. No dependency, lockfile, schema or production state is
involved, so there is no data rollback.
